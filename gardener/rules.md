# Gardener Rules

## Protected Modules

- `src/components/Bonfire/flameModel.ts` because Holds the fire engine that derives strength, out-state, and visual size; the spec requires it to be deterministic and order-independent.
- `src/domain/achievements.ts` because Derives streak and time flame unlocks from the full score calendar; errors here would wrongly unlock or relock flames.
- `src/domain/flames.ts` because Defines the flame catalog and the one-achievement-per-flame mapping, with Amber as the always-unlocked default.
- `src/hooks/useSettings.ts` because Owns the active flame selection and persistence path, which must survive restarts and migrate v1 flameColor values to v2.
- `src/theme/palettes.ts` because Source of per-flame palettes that drive halo, glow, and ember recoloring; changes alter the approved visual design.
- `src/components/Calendar/CalendarSheet.tsx` because Implements the swipe-up/swipe-down gesture surface and score editing; the spec fixes exact gesture and future-date rules here.
- `src/components/Settings/FlameGallery.tsx` because Enforces locked-flame selection rejection with feedback, so changes could make locked flames selectable.
- `src/screens/BonfireScreen.tsx` because Composes the single-screen fire view and its gesture and gear-tap behavior, which the spec sets as the main UX contract.
- `src/components/Bonfire/FireScene.tsx` because Renders the Skia/Reanimated scene that must hold 120 FPS and respect out-state visuals over equipped styles.
- `src/domain/fire.ts` because The fire engine is the oracle for fire behavior; changes must keep the contribution mapping and extinguish rules matching the documented behavior table and be covered by fire.test.ts. (from specs/001-bonfire-productivity-tracker/contracts/fire-engine.md#Contract: Fire Engine (`src/domain/fire.ts`))
- `src/data/entriesStore.ts` because Persistence must never throw on corrupt or missing data and must round-trip saved entries, so changes need review. (from specs/001-bonfire-productivity-tracker/contracts/entries-store.md#Contract: Entries Store (`src/data/entriesStore.ts`) & `u...)
- `src/data/settingsStore.ts` because Settings loading must never throw and must fall back to the Amber default on invalid data, so changes need review. (from specs/001-bonfire-productivity-tracker/contracts/settings-store.md#Contract: Settings Store (`src/data/settingsStore.ts`) &...)
- `src/domain/fire.ts` because Pure fire engine that is the test oracle for fire state; contract forbids I/O, React, or Date.now(), so changes can silently alter every derived fire state.
- `src/data/entriesStore.ts` because Sole persistence boundary for scores and notes; the contract requires loadEntries never to throw and a round trip to deep-equal saved data.
- `src/data/settingsStore.ts` because Persists the flame color preference; the contract requires invalid values to fall back to Amber and round trips to be exact.
- `src/hooks/useEntries.ts` because Enforces score validation (1..5, no future dates) and ordered persistence, and derives fire via useMemo; contract-mandated behavior lives here.
- `src/components/Bonfire/flameModel.ts` because Pure flame math with contract guarantees (intensity(0)===0, strict monotonicity, soft cap) checked by flameModel.test.ts.
- `src/domain/achievements.ts` because Derives unlockable flame styles from streak and time thresholds; changes can revoke or grant user progress.
- `src/domain/flames.ts` because Flame style catalog that achievements and settings depend on; renaming or removing ids breaks saved selections.
- `src/hooks/useSettings.ts` because Validates the flame color enum and persists it; flagged for ownership risk and tied to FR 016/017.
- `src/theme/palettes.ts` because Palettes are ported from the design source for visual parity; edits change the flame look that the spec and design expect.
- `src/components/Calendar/CalendarSheet.tsx` because Hosts the swipe-up calendar that is the only UI path for logging, editing, and clearing scores, so regressions block core use.
- `src/screens/BonfireScreen.tsx` because Top-level screen wiring stores, hooks, and the Skia scene together; flagged by analysis for import-cycle and ownership risk.
- `jest.setup.js` because Global test environment setup (including AsyncStorage mocking the contract tests rely on); changes can make all tests pass or fail spuriously.

## Never-Touch Paths

- `specs/**` because Product specs, contracts, and plans are the authoritative scope and must not be edited by automated changes.
- `unlock logic` because Existing flame unlock logic must remain unchanged; visual profiles must not add, remove, weaken, or strengthen any achievement condition. (from specs/004-flame-visual-profiles/spec.md#Functional Requirements)
- `flame selection storage` because Existing flame selection storage must remain unchanged; visual profile data must not require new persisted user data. (from specs/004-flame-visual-profiles/spec.md#Functional Requirements)
- `gallery behavior` because Existing gallery behavior must remain unchanged, including locked flame display, selection eligibility, active-state display, and rejection behavior for unavailable flames. (from specs/004-flame-visual-profiles/spec.md#Functional Requirements)
- `fire strength math` because Existing fire strength math must remain unchanged; visual profiles may define strength responses only if the same strength value and thresholds keep producing the same gameplay state. (from specs/004-flame-visual-profiles/spec.md#Functional Requirements)
- `src/domain/fireStrength.ts` because The fire strength math must not be modified, because Fire Health is visual-only and must not change fire strength values. (from specs/007-fire-health/contracts/fire-health-behavior.md#Fire Health Behavior Contract)
- `**/.env*` because secrets must never be modified by Gardener.
- `**/secrets/**` because secret material requires human handling.
- `gardener/**` because Gardener's own rules change only through a reviewed constitution PR.
- `GARDENER.md` because Gardener's own rules change only through a reviewed constitution PR.
- `specs/**` because Product specs and contracts are the authoritative statement of scope and fix policy and are maintained by humans.
- `.agents/skills/**` because Agent skill files define project workflow instructions and are not application code.
- `.claude/skills/**` because Agent skill files define project workflow instructions and must stay in sync with the spec kit tooling.
- `src/data/**/v1 storage key literal` because The versioned AsyncStorage key is the migration anchor for saved scores; renaming it without a migration loses user data.

## Autonomous Fixes Allowed

- `lint_format`: kept from the current constitution
- Under the current no_autonomy classification, make no autonomous code changes; only report findings.
- If autonomy is later permitted, limit to prettier formatting and eslint --fix on non-protected files under src/components/Settings or __tests__ with no behavior change.

## Assisted Fixes Allowed

- `dependency_patch`: kept from the current constitution
- `tests`: Adding unit tests for pure domain logic (achievements, flames, flameModel) is low-risk and cannot change runtime behavior
- `complexity_reduction`: Splitting large render or gesture components touches Skia/Reanimated timing and gesture handling, so a human should verify visual and gesture parity
- Type-level fixes under strict TypeScript that preserve runtime behavior in src/components and src/hooks, reviewed by a maintainer.
- Adding missing unit tests for contract guarantees (for example, fire.ts behavior table rows or settingsStore invalid-color fallback) without changing production logic.
- Dependency patch updates for jest-expo, eslint-config-expo, or @types packages, verified by the full test run.

## Advisory-Only Areas

- `migrations`: Changes to persisted AsyncStorage keys (bonfire.settings.v2 and v1 flameColor migration) risk losing user data, so only advise on them
- Fire scoring rules (gap tolerance, strength contribution curve, extinguish policy) because they are product decisions defined in the spec.
- Skia and Reanimated rendering performance on device, which needs manual inspection.
- Achievement thresholds and unlock timing for collectible flame styles.
- Fire Health labels (Faint, Steady, Bright, Radiant) and atmosphere tuning from local time.
