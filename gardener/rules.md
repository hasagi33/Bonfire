# Gardener Rules

## Protected Modules

- `src/components/Bonfire/flameModel.ts` because The flame visual math (intensity soft cap, height, glow) is contract-defined and must keep its stated guarantees. (from specs/001-bonfire-productivity-tracker/contracts/flame-and-theme.md#Contract: Flame Model & Theme (`src/components/Bonfire/fl...)
- `src/domain/achievements.ts` because Computes streak and time achievement unlocks, including the D+W window and the no-banking rule, so changes can silently alter which flames unlock.
- `src/hooks/useSettings.ts` because Persists the active flame selection and migrates the v1 flameColor setting to v2 with unknown-id fallback, so a bug can lose user settings on upgrade.
- `src/theme/palettes.ts` because Holds the Amber, Crimson, and Sapphire gradient and embered palettes that the spec requires to remain distinct and consistent.
- `src/screens/BonfireScreen.tsx` because Owns the cold-start loading placeholder, the upward-swipe calendar gesture alongside settings taps, and the out-state precedence over equipped flames.
- `src/components/Bonfire/Flame.tsx` because Renderer must stay generic and data-driven, selecting effects by profile tokens and never branching on flame id, to keep hot-path performance at >=120 FPS. (from specs/004-flame-visual-profiles/plan.md#Implementation Plan: Flame Visual Profiles)
- `src/components/Calendar/CalendarSheet.tsx` because Implements backward-only month paging and the swipe-up and swipe-down sheet behavior, both spec-defined.
- `src/domain/fire.ts` because The fire engine is the deterministic test oracle; changes must keep contribution(score)=max(0,score-1) and the streak walk behavior in the contract table. (from specs/001-bonfire-productivity-tracker/contracts/fire-engine.md#Contract: Fire Engine (`src/domain/fire.ts`))
- `src/data/entriesStore.ts` because Storage key bonfire.entries.v1 is versioned for future migration and loadEntries must never throw; changes need review. (from specs/001-bonfire-productivity-tracker/contracts/entries-store.md#Contract: Entries Store (`src/data/entriesStore.ts`) & `u...)
- `src/data/settingsStore.ts` because Storage key bonfire.settings.v1 is versioned and loadSettings must never throw, falling back to Amber on invalid data. (from specs/001-bonfire-productivity-tracker/contracts/settings-store.md#Contract: Settings Store (`src/data/settingsStore.ts`) &...)
- `src/components/Bonfire/Embers.tsx` because Particle pipeline must stay deterministic and UI-thread driven with no per-frame React state, to preserve >=60 FPS UI interactions. (from specs/004-flame-visual-profiles/plan.md#Implementation Plan: Flame Visual Profiles)
- `src/hooks/useEntries.ts` because Enforces score validation (1..5, no future dates) and ordered persistence, and derives fire via useMemo; contract-mandated behavior lives here.
- `src/domain/flames.ts` because Flame style catalog that achievements and settings depend on; renaming or removing ids breaks saved selections.
- `jest.setup.js` because Global test environment setup (including AsyncStorage mocking the contract tests rely on); changes can make all tests pass or fail spuriously.

## Never-Touch Paths

- `specs/**/contracts/**` because Contract documents such as the settings store v2 contract are frozen interface definitions that only humans should change.
- `gardener/**` because This directory is the maintenance tooling itself; automated changes to it could disable or alter the policy that governs them.
- `BonfireDesign/` because BonfireDesign/ is a build-time design reference and must not be modified by the maintenance bot. (from specs/001-bonfire-productivity-tracker/plan.md#Implementation Plan: Bonfire Productivity Tracker)
- `src/domain/flames.ts` because Existing flame unlock logic must remain unchanged; adding visual profiles must not add, remove, weaken, or strengthen any achievement condition. (from specs/004-flame-visual-profiles/spec.md#Functional Requirements)
- `src/domain/fireStrength.ts` because Fire strength math must not be modified by the Fire Health work, because Fire Health is visual-only and must not change fire strength values. (from specs/007-fire-health/contracts/fire-health-behavior.md#Fire Health Behavior Contract)
- `**/.env*` because secrets must never be modified by Gardener.
- `**/secrets/**` because secret material requires human handling.
- `GARDENER.md` because Gardener's own rules change only through a reviewed constitution PR.
- `specs/**` because the product specs are the source of truth Gardener checks code against.
- `.agents/skills/**` because Agent skill files define project workflow instructions and are not application code.
- `.claude/skills/**` because Agent skill files define project workflow instructions and must stay in sync with the spec kit tooling.
- `src/data/**/v1 storage key literal` because The versioned AsyncStorage key is the migration anchor for saved scores; renaming it without a migration loses user data.
- `legal/qa-cod120-counsel/**` because outside counsel owns these contract drafts; they must stay byte-identical.

## Autonomous Fixes Allowed

- `lint_format`: kept from the current constitution
- Under the current no_autonomy classification, make no autonomous code changes; only report findings.
- If autonomy is later permitted, limit to prettier formatting and eslint --fix on non-protected files under src/components/Settings or __tests__ with no behavior change.

## Assisted Fixes Allowed

- `dependency_patch`: kept from the current constitution
- `tests`: Adding or fixing Jest tests in __tests__ is low risk and verifiable, and the fire and achievement logic is pure enough to test without device rendering
- `complexity_reduction`: Splitting large fire, achievement, or render functions risks subtle changes to deterministic recomputation and 120 FPS rendering, so a human should review each change
- Type-level fixes under strict TypeScript that preserve runtime behavior in src/components and src/hooks, reviewed by a maintainer.
- Adding missing unit tests for contract guarantees (for example, fire.ts behavior table rows or settingsStore invalid-color fallback) without changing production logic.
- Dependency patch updates for jest-expo, eslint-config-expo, or @types packages, verified by the full test run.

## Advisory-Only Areas

- `api_behavior`: Changes to the locked-selection behavior need review and must keep the equip rule that locked flames never equip (source: specs/003-ui-flame-polish/tasks.md#Tasks: UI & Flame Polish Fixes)
- `migrations`: The v1 flameColor to v2 settings migration in AsyncStorage is a one-time data migration; only advise on it, since a mistake can strand existing user choices
- Fire scoring rules (gap tolerance, strength contribution curve, extinguish policy) because they are product decisions defined in the spec.
- Skia and Reanimated rendering performance on device, which needs manual inspection.
- Achievement thresholds and unlock timing for collectible flame styles.
- Fire Health labels (Faint, Steady, Bright, Radiant) and atmosphere tuning from local time.
