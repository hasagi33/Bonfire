# Gardener Rules

## Protected Modules

- `src/domain/achievements.ts` because Defines streak and time achievement rules, which the spec requires to be derived deterministically from the full score calendar and today's date.
- `src/domain/flames.ts` because Flame catalog holds unlock achievements and palette data for all 20 flames; adding visualProfile data here must preserve unlock conditions and identity, so changes need human review. (from specs/004-flame-visual-profiles/plan.md#Implementation Plan: Flame Visual Profiles)
- `src/components/Bonfire/flameModel.ts` because Pure profile-to-render helpers and strength response must leave fire strength math unchanged; changes need human review. (from specs/004-flame-visual-profiles/plan.md#Implementation Plan: Flame Visual Profiles)
- `src/components/Bonfire/Flame.tsx` because The Skia flame must keep design fidelity to BonfireDesign screenshots and the blur/gradient/screen-blend stack; it must not reduce blur passes, layers, or particle counts to chase frame rate. (from specs/001-bonfire-productivity-tracker/research.md#Phase 0 Research: Bonfire Productivity Tracker (design-fa...)
- `src/components/Bonfire/Embers.tsx` because Shared particle pipeline must follow the BonfireDesign particle mix and keep >=120 FPS flame rendering; changes need human review. (from specs/004-flame-visual-profiles/plan.md#Implementation Plan: Flame Visual Profiles)
- `src/components/Bonfire/FireScene.tsx` because Composes the bonfire scene and its atmosphere, so changes here can break the single-screen living-fire requirement and the no-continuous-JS-timer constraint.
- `src/components/Bonfire/Hearth.tsx` because Renders the hearth and logs as part of the required full-fidelity flame composition.
- `src/components/Bonfire/FireCaption.tsx` because Displays fire health and state text derived from score history, so it must stay consistent with the derived fire state.
- `src/components/Calendar/CalendarSheet.tsx` because Implements the swipe-up calendar that edits past scores and enforces backward-only month paging, both spec-defined behaviors.
- `src/components/Calendar/ScorePickerBar.tsx` because Controls the 1-5 score entry and clearing, which is the core write path for scores that drive the fire.
- `src/components/Settings/FlameGallery.tsx` because Shows locked and unlocked status, requirements, and live progress, which must match the derived achievement state exactly.
- `src/components/Settings/SettingsSheet.tsx` because Hosts the flame and color selection persisted across restarts, and the spec requires the gear tap to keep working alongside the calendar swipe.
- `src/hooks/useSettings.ts` because Mediates persisted settings (active flame and color) and the load-before-render behavior, where a bug could discard scores or flash an unlit fire.
- `src/screens/BonfireScreen.tsx` because Passing activeStyle into Flame and Embers must not change unlock, storage, gallery, or fire strength behavior; changes need human review. (from specs/004-flame-visual-profiles/plan.md#Source Code (repository root))
- `src/theme/palettes.ts` because Defines the Amber, Crimson, and Sapphire palettes and the embered variants, where Amber must never render embered.
- `src/domain/atmosphere.ts` because The atmosphere helper is derived-state logic; changes must keep readability and the day/night/season mood behavior intact. (from specs/006-subtle-atmosphere/plan.md#Implementation Plan: Subtle Atmosphere)
- `src/domain/fire.ts` because Pure fire engine that is the test oracle for fire state; contract forbids I/O, React, or Date.now(), so changes can silently alter every derived fire state.
- `src/data/entriesStore.ts` because Sole persistence boundary for scores and notes; the contract requires loadEntries never to throw and a round trip to deep-equal saved data.
- `src/data/settingsStore.ts` because Persists the flame color preference; the contract requires invalid values to fall back to Amber and round trips to be exact.
- `src/hooks/useEntries.ts` because Enforces score validation (1..5, no future dates) and ordered persistence, and derives fire via useMemo; contract-mandated behavior lives here.
- `src/components/Bonfire/flameModel.ts` because Pure flame math with contract guarantees (intensity(0)===0, strict monotonicity, soft cap) checked by flameModel.test.ts.
- `src/domain/achievements.ts` because Derives unlockable flame styles from streak and time thresholds; changes can revoke or grant user progress.
- `src/domain/flames.ts` because Flame style catalog that achievements and settings depend on; renaming or removing ids breaks saved selections.
- `src/hooks/useSettings.ts` because Validates the flame color enum and persists it; flagged for ownership risk and tied to FR 016/017.
- `src/theme/palettes.ts` because Palettes are ported from the design source for visual parity; edits change the flame look that the spec and design expect.
- `src/components/Calendar/CalendarSheet.tsx` because Hosts the swipe-up calendar that is the only UI path for logging, editing, and clearing scores, so regressions block core use.
- `src/screens/BonfireScreen.tsx` because Top-level screen wiring stores, hooks, and the Skia scene together; flagged by analysis for import-cycle and ownership risk.
- `jest.setup.js` because Global test environment setup (including AsyncStorage mocking the contract tests rely on); changes can make all tests pass or fail spuriously.

- `gardener/**` because This is the maintenance tool's own configuration and logic, and it must not modify itself.
- `.agents/**` because These are agent instruction and skill files that govern how changes are made, not application code.
- `.claude/**` because These are agent instruction and skill files that govern how changes are made, not application code.

- `BonfireDesign/flame-renderer.jsx` because BonfireDesign/flame-renderer.jsx is the required reference renderer and must not be modified by the flame visual profiles work. (from specs/004-flame-visual-profiles/research.md#Research: Flame Visual Profiles)

- `GARDENER.md` because Gardener's own rules change only through a reviewed constitution PR.

- `.agents/skills/**` because Agent skill files define project workflow instructions and are not application code.

- `src/data/**/v1 storage key literal` because The versioned AsyncStorage key is the migration anchor for saved scores; renaming it without a migration loses user data.

## Autonomous Fixes Allowed

- `lint_format`: Lint and format fixes are acceptable only when they keep the lint-clean gate passing with zero errors, per the constitution quality gates (source: specs/001-bonfire-productivity-tracker/quickstart.md#Quickstart & Validation Guide: Bonfire Productivity Track...)
- Under the current no_autonomy classification, make no autonomous code changes; only report findings.
- If autonomy is later permitted, limit to prettier formatting and eslint --fix on non-protected files under src/components/Settings or __tests__ with no behavior change.

## Assisted Fixes Allowed

- `dependency_patch`: Dependency or Expo SDK alignment changes (Skia, Reanimated, gesture-handler, RN/React versions) must be reviewed by a human, since the SDK constrains RN versions (source: specs/001-bonfire-productivity-tracker/research.md#Phase 0 Research: Bonfire Productivity Tracker (design-fa...)
- `tests`: Adding tests under __tests__ for pure domain logic (fire engine, achievements, flame model) is low risk and cannot change app behavior
- `complexity_reduction`: Splitting large render or sheet components touches full-fidelity rendering and gesture routing, so each change needs human review of visual and behavior parity
- Type-level fixes under strict TypeScript that preserve runtime behavior in src/components and src/hooks, reviewed by a maintainer.
- Adding missing unit tests for contract guarantees (for example, fire.ts behavior table rows or settingsStore invalid-color fallback) without changing production logic.
- Dependency patch updates for jest-expo, eslint-config-expo, or @types packages, verified by the full test run.

## Advisory-Only Areas

- `requirement_mismatch`: Fire, streak, and unlock rules are spec-defined and changes should be proposed for human review against the spec rather than auto-corrected
- Fire scoring rules (gap tolerance, strength contribution curve, extinguish policy) because they are product decisions defined in the spec.
- Skia and Reanimated rendering performance on device, which needs manual inspection.
- Achievement thresholds and unlock timing for collectible flame styles.
- Fire Health labels (Faint, Steady, Bright, Radiant) and atmosphere tuning from local time.
