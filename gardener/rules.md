# Gardener Rules

## Protected Modules

- `src/components/Bonfire/flameModel.ts` because The fire strength math and flame model drive gameplay state; changes must keep the same numeric strength results and thresholds. (from specs/004-flame-visual-profiles/spec.md#Functional Requirements)
- `src/domain/achievements.ts` because The achievement engine determines unlock state; it must be deterministic, order-independent, recompute on any change, and must not reward low scores or intentional streak/fire breaks. (from specs/002-achievement-flame-unlocks/data-model.md#EffectiveRender — what `useFlames` hands the screen)
- `src/domain/flames.ts` because The flame catalog defines unlock conditions, time windows and palettes for every flame; changes must keep the difficulty ordering base < streak < time by rarity and keep every non-base flame with an achievement, palette and embered variant. (from specs/002-achievement-flame-unlocks/data-model.md#EffectiveRender — what `useFlames` hands the screen)
- `src/theme/palettes.ts` because Holds flame palettes and the embered dim/desaturate variant, where Amber must never render embered and glow colors derive from the active palette.
- `src/hooks/useSettings.ts` because Persists the active flame-style id locally, and changes here can break the required restart persistence and immediate recolor behavior.
- `src/components/Bonfire/Flame.tsx` because The Skia flame is the hero render path and must keep its per-frame animation free of achievement computation; the change is only an optional dim knob with colors still from the palette prop. (from specs/002-achievement-flame-unlocks/plan.md#Implementation Plan: Achievement-Locked Flame Styles)
- `src/components/Bonfire/FireScene.tsx` because Composes the animated scene and out-state visuals (charred logs, smoke, no flame or embers when out), so changes can break the out-state precedence rule and full-fidelity rendering.
- `src/components/Bonfire/Embers.tsx` because Particle rendering must stay on the UI thread with memoized profile-derived data and no per-frame React state, to preserve performance targets. (from specs/004-flame-visual-profiles/plan.md#Implementation Plan: Flame Visual Profiles)
- `src/components/Bonfire/Hearth.tsx` because Hearth warm wash is a palette-derived visual that must recolor with the active flame and must not add continuous JS timers.
- `src/screens/BonfireScreen.tsx` because Owns the main view gesture wiring: swipe-up opens the calendar anywhere on the closed view while gear and day-cell taps must still work.
- `src/components/Calendar/CalendarSheet.tsx` because The closed-state calendar open gesture changes to a full-screen upward Pan that must not steal taps from the settings gear; the gesture activates only on vertical-up movement. (from specs/002-achievement-flame-unlocks/plan.md#Implementation Plan: Achievement-Locked Flame Styles)
- `src/components/Calendar/ScorePickerBar.tsx` because Handles assigning, changing, and clearing integer scores 1–5 on past and current days, where validation of future dates and out-of-range values lives.
- `src/components/Settings/FlameGallery.tsx` because Lists every flame with locked/unlocked status, requirement, and live progress, and the locked-selection guard depends on it.
- `src/components/Settings/SettingsSheet.tsx` because Hosts the flame selection entry point, where locked flames must show a rejection cue and remain unequipped.
- `src/data/` because Local-only persistence of the score map and flame selection; loaders must never throw on corrupt data and must show a placeholder until loads finish.
- `.eslintrc.js` because Shared lint configuration; changes alter the check standard for every file in the repository.
- `jest.setup.js` because Shared Jest environment setup for Skia, Reanimated, and AsyncStorage mocks; changes can silently alter what every test exercises.
- `src/domain/fireMetrics.ts` because The run-metrics walk must be a single deterministic pass with today injected, so achievement results are order-independent and testable. (from specs/002-achievement-flame-unlocks/plan.md#Implementation Plan: Achievement-Locked Flame Styles)
- `src/data/settingsStore.ts` because The settings store schema changes (v1 flameColor to v2 flameStyle id) must migrate existing v1 data; the active flame selection must persist and may load locked, rendering embered. (from specs/002-achievement-flame-unlocks/plan.md#Implementation Plan: Achievement-Locked Flame Styles)
- `src/hooks/useFlames.ts` because useFlames is the single memoized junction between derived achievement state and the UI; it must be memoized on (entries, today, fire) and must not recompute per frame. (from specs/002-achievement-flame-unlocks/plan.md#Implementation Plan: Achievement-Locked Flame Styles)
- `src/domain/fire.ts` because Pure fire engine that is the test oracle for fire state; contract forbids I/O, React, or Date.now(), so changes can silently alter every derived fire state.
- `src/data/entriesStore.ts` because Sole persistence boundary for scores and notes; the contract requires loadEntries never to throw and a round trip to deep-equal saved data.
- `src/hooks/useEntries.ts` because Enforces score validation (1..5, no future dates) and ordered persistence, and derives fire via useMemo; contract-mandated behavior lives here.

## Never-Touch Paths

- `specs/**` because Product specs are the authoritative statement of scope and fix/no-fix policy, so automated changes must not rewrite them.
- `gardener/**` because This is the maintenance tool's own directory, and the tool should not edit its own policy or configuration.
- `src/domain/streak*` because Streak survival rules must not be modified by the Fire Health work because Fire Health is visual-only and must not change streak survival outcomes. (from specs/007-fire-health/contracts/fire-health-behavior.md#Fire Health Behavior Contract)
- `**/.env*` because secrets must never be modified by Gardener.
- `**/secrets/**` because secret material requires human handling.
- `GARDENER.md` because Gardener's own rules change only through a reviewed constitution PR.
- `.agents/skills/**` because Agent skill files define project workflow instructions and are not application code.
- `.claude/skills/**` because Agent skill files define project workflow instructions and must stay in sync with the spec kit tooling.
- `src/data/**/v1 storage key literal` because The versioned AsyncStorage key is the migration anchor for saved scores; renaming it without a migration loses user data.

## Autonomous Fixes Allowed

- `lint_format`: kept from the current constitution
- Under the current no_autonomy classification, make no autonomous code changes; only report findings.
- If autonomy is later permitted, limit to prettier formatting and eslint --fix on non-protected files under src/components/Settings or __tests__ with no behavior change.

## Assisted Fixes Allowed

- `dependency_patch`: kept from the current constitution
- `tests`: Adding unit tests for pure domain logic (score-to-strength, two-miss extinguish, time windows) is low risk and does not change runtime behavior
- `complexity_reduction`: Splitting large render or gesture components like FireScene or CalendarSheet needs human review to confirm rendered output and gesture behavior are unchanged
- Type-level fixes under strict TypeScript that preserve runtime behavior in src/components and src/hooks, reviewed by a maintainer.
- Adding missing unit tests for contract guarantees (for example, fire.ts behavior table rows or settingsStore invalid-color fallback) without changing production logic.
- Dependency patch updates for jest-expo, eslint-config-expo, or @types packages, verified by the full test run.

## Advisory-Only Areas

- `layer_violation_repair`: Changes that let components or other modules access AsyncStorage directly, or that move persistence or formatting into the fire engine, violate the layering and should only be suggested (source: specs/001-bonfire-productivity-tracker/contracts/entries-store.md#Contract: Entries Store (`src/data/entriesStore.ts`) & `u...)
- `requirement_mismatch`: Spec-versus-code mismatches such as time-window or backfill semantics involve product decisions, so the tool should report them for a human rather than edit code
- Fire scoring rules (gap tolerance, strength contribution curve, extinguish policy) because they are product decisions defined in the spec.
- Skia and Reanimated rendering performance on device, which needs manual inspection.
- Achievement thresholds and unlock timing for collectible flame styles.
- Fire Health labels (Faint, Steady, Bright, Radiant) and atmosphere tuning from local time.
