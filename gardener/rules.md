# Gardener Rules

## Protected Modules

- `src/domain/fire.ts` because The fire engine is the deterministic oracle for fire state and must match the behavior table and guarantees in the contract; changes need review. (from specs/001-bonfire-productivity-tracker/contracts/fire-engine.md#Contract: Fire Engine (`src/domain/fire.ts`))
- `src/domain/fireMetrics.ts` because Derives streak and strength metrics that the achievement unlock contract depends on, so changes can silently alter unlock state.
- `src/domain/achievements.ts` because Achievement engine decides time-window and streak unlocks that the spec requires to be order-independent and recomputed from the full calendar.
- `src/domain/flames.ts` because Changes to flame catalog visualProfile data must keep all 20 flames in strict parity with the BonfireDesign source of truth; this file also holds unlock conditions and storage-relevant identity, so changes need human review. (from specs/004-flame-visual-profiles/plan.md#Implementation Plan: Flame Visual Profiles)
- `src/data/entriesStore.ts` because Persistence must never throw and must round-trip entries exactly; corrupt data resolves to an empty map. (from specs/001-bonfire-productivity-tracker/contracts/entries-store.md#Contract: Entries Store (`src/data/entriesStore.ts`) & `u...)
- `src/data/settingsStore.ts` because Settings loading must never throw and must fall back to Amber for invalid flame colors. (from specs/001-bonfire-productivity-tracker/contracts/settings-store.md#Contract: Settings Store (`src/data/settingsStore.ts`) &...)
- `src/hooks/useSettings.ts` because Holds the v1 Amber/Crimson/Sapphire to v2 flame style migration logic; changes can reset or corrupt existing users' chosen flame.
- `src/components/Bonfire/flameModel.ts` because The flame visual mapping (height, glow, intensity soft cap) is specified exactly and must keep its guarantees. (from specs/001-bonfire-productivity-tracker/contracts/flame-and-theme.md#Contract: Flame Model & Theme (`src/components/Bonfire/fl...)
- `src/components/Bonfire/Flame.tsx` because Skia and Reanimated flame render loop; the spec forbids sustained frame drops on flame select or switch.
- `src/components/Bonfire/Embers.tsx` because Ember animation loop that must stop under reduced-motion preference, a stated accessibility requirement.
- `src/components/Bonfire/Hearth.tsx` because Renders the out-state charred logs and the rule that out visuals take precedence over equipped flames.
- `src/components/Bonfire/FireScene.tsx` because Composes the flame scene and atmosphere from local time without continuous JS timers; performance-sensitive composition.
- `src/components/Bonfire/FireCaption.tsx` because Displays Fire Health labels derived from score quality; wording and tier mapping are product-facing.
- `src/components/Calendar/CalendarSheet.tsx` because Backfill and edit of past days triggers fire and achievement recomputation; gesture and sheet behavior are spec-bound.
- `src/components/Calendar/ScorePickerBar.tsx` because Inline 1 to 5 score picker is the only write path for scores, so its value mapping must match the spec.
- `src/components/Settings/FlameGallery.tsx` because Gallery shows unlock status, requirements, and live progress; spec requires exact display of these states.
- `src/components/Settings/SettingsSheet.tsx` because Hosts flame selection and persistence entry point; selection must persist across restarts.
- `src/screens/BonfireScreen.tsx` because Top-level screen handling cold-start loading placeholder and avoiding an early unlit flash; spec-critical.
- `src/theme/palettes.ts` because Flame color palettes define the embered desaturated variants; changing values alters the approved visual identity.
- `BonfireDesign/flame-profiles.js` because BonfireDesign/flame-profiles.js is the source-of-truth data map that the 20 flame visual profiles must be derived from, so changes there need human review. (from specs/004-flame-visual-profiles/contracts/visual-profile-data.md#Contract: Visual Profile Data)
- `src/domain/fire.ts` because Pure fire engine that is the test oracle for fire state; contract forbids I/O, React, or Date.now(), so changes can silently alter every derived fire state.
- `src/data/entriesStore.ts` because Sole persistence boundary for scores and notes; the contract requires loadEntries never to throw and a round trip to deep-equal saved data.
- `src/data/settingsStore.ts` because Persists the flame color preference; the contract requires invalid values to fall back to Amber and round trips to be exact.
- `src/hooks/useEntries.ts` because Enforces score validation (1..5, no future dates) and ordered persistence, and derives fire via useMemo; contract-mandated behavior lives here.
- `src/components/Bonfire/flameModel.ts` because Pure flame math with contract guarantees (intensity(0)===0, strict monotonicity, soft cap) checked by flameModel.test.ts.
- `src/domain/achievements.ts` because Derives unlockable flame styles from streak and time thresholds; changes can revoke or grant user progress.
- `src/domain/flames.ts` because Flame style catalog that achievements and settings depend on; renaming or removing ids breaks saved selections.
- `src/hooks/useSettings.ts` because Validates the flame color enum and persists it; flagged for ownership risk and tied to FR 016/017.
- `src/theme/palettes.ts` because Palettes are ported from the design source for visual parity; edits change the flame look that the spec and design expect.
- `src/components/Calendar/CalendarSheet.tsx` because Hosts the swipe-up calendar that is the only UI path for logging, editing, and clearing scores, so regressions block core use.
- `src/screens/BonfireScreen.tsx` because Top-level screen wiring stores, hooks, and the Skia scene together; flagged by analysis for import-cycle and ownership risk.
- `jest.setup.js` because Global test environment setup (including AsyncStorage mocking the contract tests rely on); changes can make all tests pass or fail spuriously.

## Never-Touch Paths

- `specs/**` because Product specs and contracts are the authoritative scope; automation must not rewrite them.
- `gardener/**` because The maintenance tool's own configuration and code should not be edited by the change pipeline it drives.
- `src/billing/tax.ts` because src/billing/tax.ts must not be modified by the checkout redesign work. (from specs/003-ui-flame-polish/checklists/requirements.md#Specification Quality Checklist: UI & Flame Polish Fixes)
- `**/.env*` because secrets must never be modified by Gardener.
- `**/secrets/**` because secret material requires human handling.
- `GARDENER.md` because Gardener's own rules change only through a reviewed constitution PR.
- `specs/**` because Product specs and contracts are the authoritative statement of scope and fix policy and are maintained by humans.
- `.agents/skills/**` because Agent skill files define project workflow instructions and are not application code.
- `.claude/skills/**` because Agent skill files define project workflow instructions and must stay in sync with the spec kit tooling.
- `src/data/**/v1 storage key literal` because The versioned AsyncStorage key is the migration anchor for saved scores; renaming it without a migration loses user data.

## Autonomous Fixes Allowed

- `lint_format`: kept from the current constitution
- Under the current no_autonomy classification, make no autonomous code changes; only report findings.
- If autonomy is later permitted, limit to prettier formatting and eslint --fix on non-protected files under src/components/Settings or __tests__ with no behavior change.

## Assisted Fixes Allowed

- `generated_refresh`: If the original Bonfire.html design becomes fetchable, the theme tokens should be reconciled against it, which needs review (source: specs/001-bonfire-productivity-tracker/design/README.md#Design Source Note (T004))
- `dependency_patch`: kept from the current constitution
- `tests`: Adding or fixing Jest tests under __tests__ only adds coverage and does not change shipped behavior, so it is safe to merge alone
- `complexity_reduction`: Splitting functions in the fire engine, achievements, or Skia render code can change behavior or frame timing, so a maintainer should review
- `requirement_mismatch`: Where the design and the spec disagree, the spec wins on mechanics and the design wins on look-and-feel; such conflicts should be reviewed rather than resolved automatically (source: specs/001-bonfire-productivity-tracker/plan.md#Implementation Plan: Bonfire Productivity Tracker)
- Type-level fixes under strict TypeScript that preserve runtime behavior in src/components and src/hooks, reviewed by a maintainer.
- Adding missing unit tests for contract guarantees (for example, fire.ts behavior table rows or settingsStore invalid-color fallback) without changing production logic.
- Dependency patch updates for jest-expo, eslint-config-expo, or @types packages, verified by the full test run.

## Advisory-Only Areas

- `permissions`: Locked flames must never be settable as the active flame; the selection guard must reject them at the gallery row and at the screen-level persistence call (source: specs/003-ui-flame-polish/research.md#Research: UI & Flame Polish Fixes)
- `migrations`: The v1 to v2 AsyncStorage settings key migration is a storage schema change; the tool should only advise, since there is no database and a bad migration would reset users' flame choice
- Fire scoring rules (gap tolerance, strength contribution curve, extinguish policy) because they are product decisions defined in the spec.
- Skia and Reanimated rendering performance on device, which needs manual inspection.
- Achievement thresholds and unlock timing for collectible flame styles.
- Fire Health labels (Faint, Steady, Bright, Radiant) and atmosphere tuning from local time.

## Architecture Boundaries

- The fire engine must be pure and framework-free, with no I/O, no React, and no Date.now() inside; today is passed in. (sources: specs/001-bonfire-productivity-tracker/contracts/fire-engine.md#Contract: Fire Engine (`src/domain/fire.ts`))
- All persistence is isolated in the data layer, and the rest of the app must never touch AsyncStorage directly. (sources: specs/001-bonfire-productivity-tracker/contracts/entries-store.md#Contract: Entries Store (`src/data/entriesStore.ts`) & `u...)
- Fire state is derived and never stored; it is recomputed from the entries and today's date. (sources: specs/001-bonfire-productivity-tracker/data-model.md#Phase 1 Data Model: Bonfire Productivity Tracker)
- The storage keys are versioned (bonfire.entries.v1, bonfire.settings.v1) so future schema changes can migrate. (sources: specs/001-bonfire-productivity-tracker/contracts/entries-store.md#Contract: Entries Store (`src/data/entriesStore.ts`) & `u...)
- The flame model and theme tokens are pure mapping and constants with no animation or I/O, and animation lives in the rendering components. (sources: specs/001-bonfire-productivity-tracker/contracts/flame-and-theme.md#Contract: Flame Model & Theme (`src/components/Bonfire/fl...)
- The pure fire engine in src/domain must stay framework-free and mirror BonfireDesign/logic.js. (sources: specs/001-bonfire-productivity-tracker/plan.md#Constitution Check)
- The flame is isolated in Skia components with the flame math kept in a pure flameModel.ts. (sources: specs/001-bonfire-productivity-tracker/plan.md#Constitution Check)
- Persistence of scores and settings is isolated in src/data behind hooks. (sources: specs/001-bonfire-productivity-tracker/plan.md#Constitution Check)
- The intensity curve is intensity(strength) = 1 − e^(−strength/14), ported verbatim into flameModel.ts, replacing the earlier sqrt/soft-cap. (sources: specs/001-bonfire-productivity-tracker/research.md#Phase 0 Research: Bonfire Productivity Tracker (design-fa...)
- Theme tokens are ported from styles.css :root into src/theme/tokens.ts and flame palettes from app.jsx into src/theme/palettes.ts as a single source of truth. (sources: specs/001-bonfire-productivity-tracker/research.md#Phase 0 Research: Bonfire Productivity Tracker (design-fa...)
- Per-frame flicker and ember updates run on the UI thread via Reanimated shared values and never touch JS state. (sources: specs/001-bonfire-productivity-tracker/research.md#Phase 0 Research: Bonfire Productivity Tracker (design-fa...)
- The calendar's next-month control must be disabled on the current month, and the calendar must not show or edit future months (FR-020). (sources: specs/001-bonfire-productivity-tracker/research.md#Phase 0 Research: Bonfire Productivity Tracker (design-fa...)
- The app must be migrated to Expo, with the flame rendered via Skia and the calendar revealed by a swipe-up sheet, matching BonfireDesign/. (sources: specs/001-bonfire-productivity-tracker/tasks.md#Tasks: Bonfire Productivity Tracker)
- Achievement unlock state is never stored and is derived on every read from the calendar and today (FR-004), with the date-to-score map as the single source of truth. (sources: specs/002-achievement-flame-unlocks/plan.md#Implementation Plan: Achievement-Locked Flame Styles; specs/002-achievement-flame-unlocks/research.md#Phase 0 Research: Achievement-Locked Flame Styles)
- Achievement state must be recomputed order-independently from the calendar, so backfill, edit, and clear produce the same result regardless of edit order (FR-020, SC-005). (sources: specs/002-achievement-flame-unlocks/data-model.md#EffectiveRender — what `useFlames` hands the screen)
- The flame catalog (visuals, achievement conditions, time windows) must live in one editable data source, src/domain/flames.ts, so tuning a flame needs no engine or UI changes. (sources: specs/002-achievement-flame-unlocks/plan.md#Implementation Plan: Achievement-Locked Flame Styles; specs/002-achievement-flame-unlocks/tasks.md#Tasks: Achievement-Locked Flame Styles)
- computeFire in src/domain/fire.ts stays the source of truth for lit/out/strength behavior and is reused unchanged, while new run metrics go in a separate pure module so feature 001 remains green. (sources: specs/002-achievement-flame-unlocks/plan.md#Implementation Plan: Achievement-Locked Flame Styles; specs/002-achievement-flame-unlocks/research.md#Phase 0 Research: Achievement-Locked Flame Styles; specs/002-achievement-flame-unlocks/spec.md#Key Entities *(include if feature involves data)*)
- Achievement evaluation stays out of the per-frame animation and Skia render path: it is memoized on (entries, today), and switching the active flame only swaps the palette fed to the Skia Flame. (sources: specs/002-achievement-flame-unlocks/plan.md#Implementation Plan: Achievement-Locked Flame Styles; specs/002-achievement-flame-unlocks/tasks.md#Tasks: Achievement-Locked Flame Styles)
- Achievement state must never enter the UI-thread flicker clock or add per-frame work (SC-010 inherits feature 001's 120 FPS bar). (sources: specs/002-achievement-flame-unlocks/plan.md#Implementation Plan: Achievement-Locked Flame Styles)
- The Flame component's colors must come from the palette prop, which is now per-flame. (sources: specs/002-achievement-flame-unlocks/plan.md#Implementation Plan: Achievement-Locked Flame Styles)
- A locked flame is rendered with its embered palette and dim value, and an unlocked active flame uses its full palette and dim 1, derived from activeUnlocked. (sources: specs/002-achievement-flame-unlocks/data-model.md#EffectiveRender — what `useFlames` hands the screen)
- Streak achievements unlock only while the current run satisfies the condition and the fire is lit, and they relock when the fire goes out or an edit drops the run below the condition. (sources: specs/002-achievement-flame-unlocks/data-model.md#EffectiveRender — what `useFlames` hands the screen)
- Time achievements unlock when the completion is today within the window and the fire is lit; they relock when the window (D+W) passes or the fire goes out, and re-completing restarts the window from the new day without banking. (sources: specs/002-achievement-flame-unlocks/data-model.md#EffectiveRender — what `useFlames` hands the screen)
- Unlock requirements must never reward low scores or intentional streak or fire breaks (FR-011a, FR-011b). (sources: specs/002-achievement-flame-unlocks/data-model.md#EffectiveRender — what `useFlames` hands the screen)
- Achievement difficulty must strictly increase base < streak < time by rarity, verified by the catalog test (FR-011, SC-009). (sources: specs/002-achievement-flame-unlocks/data-model.md#EffectiveRender — what `useFlames` hands the screen)
- Every non-base flame must have an achievement, and every flame must have a palette and an embered variant (FR-001, FR-024). (sources: specs/002-achievement-flame-unlocks/data-model.md#EffectiveRender — what `useFlames` hands the screen)
- Time achievements must define windowDays (FR-007). (sources: specs/002-achievement-flame-unlocks/data-model.md#EffectiveRender — what `useFlames` hands the screen)
- When the fire is out, all non-Amber locked flames and out-state visuals take precedence (FR-007a, FR-015). (sources: specs/002-achievement-flame-unlocks/data-model.md#EffectiveRender — what `useFlames` hands the screen)
- The active flame selection persists and may load in a locked state, rendering as embered (FR-021, FR-014, SC-006, SC-007). (sources: specs/002-achievement-flame-unlocks/data-model.md#EffectiveRender — what `useFlames` hands the screen)
- The constitution requires strict TypeScript with no any, framework-free pure modules in src/domain, and explanatory comments in new modules, hooks, and components. (sources: specs/002-achievement-flame-unlocks/plan.md#Constitution Check)
- Unlock states must not be stored; only the active flame selection is persisted. (sources: specs/002-achievement-flame-unlocks/research.md#Phase 0 Research: Achievement-Locked Flame Styles; specs/002-achievement-flame-unlocks/spec.md#Functional Requirements; specs/004-flame-visual-profiles/spec.md#Functional Requirements)
- Achievement conditions are expressed as a closed set of pure condition kinds referenced by catalog rows, so new flames are added by catalog entries and tuned by numeric parameters. (sources: specs/002-achievement-flame-unlocks/research.md#Phase 0 Research: Achievement-Locked Flame Styles)
- Gradient flames map onto the existing five-stop Palette consumed by Flame.tsx, reusing the existing flame composition without a new flame renderer. (sources: specs/002-achievement-flame-unlocks/spec.md#Functional Requirements)
- The active flame selection supersedes the previous single fire color preference, and existing Amber/Crimson/Sapphire color choices must map to the corresponding flame style on upgrade. (sources: specs/002-achievement-flame-unlocks/spec.md#Key Entities *(include if feature involves data)*)

- Calendar score-button and day-cell colors must both be read from the single token source in tokens.ts/heatStyle(), and the two surfaces must not diverge into separate ramps. (sources: specs/003-ui-flame-polish/research.md#R3. Score heat ramp white→red (P3))
- Locked flames must not be hidden; they remain visible in the gallery as an embered preview and only become non-selectable. (sources: specs/003-ui-flame-polish/research.md#Research: UI & Flame Polish Fixes)
