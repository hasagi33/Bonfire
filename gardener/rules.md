# Gardener Rules

## Protected Modules

- `src/domain/achievements.ts` because Holds the streak and time achievement unlock logic, which the spec requires to be deterministic, independent of edit order, and tied to a lit fire.
- `src/domain/flames.ts` because Defines the 20-flame catalog (1 base, 8 streak, 11 time) with exact conditions and windows, and the spec forbids conditions that reward low or lowered scores or breaking a streak.
- `src/components/Bonfire/flameModel.ts` because The intensity curve (1 - e^(-s/14)), height, glow, and brightness mapping must be kept to match the design; changes need review. (from specs/001-bonfire-productivity-tracker/research.md#Phase 0 Research: Bonfire Productivity Tracker (design-fa...)
- `src/hooks/useSettings.ts` because Wraps the settings store, including the v1 flameColor to v2 flameStyle migration, fallback to 'amber' for unknown ids, and fire-and-forget persistence.
- `src/components/Calendar/CalendarSheet.tsx` because Implements the swipe-up calendar sheet, the cap on navigating past the current month, and the requirement that open gestures not steal taps from the gear or day cells.
- `src/screens/BonfireScreen.tsx` because Owns cold-start loading gating until entries and settings are ready, which prevents an unlit flash and keeps a score entered during loading from being discarded.
- `src/components/Bonfire/Flame.tsx` because Renders the flame, including embered dim variants for locked flames and reduced-motion handling that must stop animation loops.
- `src/theme/palettes.ts` because Flame palettes are ported from app.jsx and must stay faithful to the design; changes need review. (from specs/001-bonfire-productivity-tracker/research.md#Phase 0 Research: Bonfire Productivity Tracker (design-fa...)
- `src/domain/fire.ts` because The fire engine defines the core streak and strength rules and must match BonfireDesign/logic.js; changes need human review. (from specs/001-bonfire-productivity-tracker/plan.md#Constitution Check)
- `src/theme/tokens.ts` because Theme tokens are ported from styles.css :root as the single source of visual truth; changes need review. (from specs/001-bonfire-productivity-tracker/plan.md#Constitution Check)
- `src/data/entriesStore.ts` because The persisted date-to-score store holds user data; changes to its persistence need human review. (from specs/001-bonfire-productivity-tracker/plan.md#Constitution Check)
- `src/data/settingsStore.ts` because The persisted flame color setting needs human review because it affects stored user data. (from specs/001-bonfire-productivity-tracker/plan.md#Constitution Check)
- `src/domain/fire.ts` because Pure fire engine that is the test oracle for fire state; contract forbids I/O, React, or Date.now(), so changes can silently alter every derived fire state.
- `src/data/entriesStore.ts` because Sole persistence boundary for scores and notes; the contract requires loadEntries never to throw and a round trip to deep-equal saved data.
- `src/data/settingsStore.ts` because Persists the flame color preference; the contract requires invalid values to fall back to Amber and round trips to be exact.
- `src/hooks/useEntries.ts` because Enforces score validation (1..5, no future dates) and ordered persistence, and derives fire via useMemo; contract-mandated behavior lives here.
- `src/components/Bonfire/flameModel.ts` because Pure flame math with contract guarantees (intensity(0)===0, strict monotonicity, soft cap) checked by flameModel.test.ts.
- `src/domain/achievements.ts` because Derives unlockable flame styles from streak and time thresholds; changes can revoke or grant user progress.
- `src/domain/flames.ts` because Flame style catalog that achievements and settings depend on; renaming or removing ids breaks saved selections.
- `src/hooks/useSettings.ts` because Validates the flame color enum and persists it; flagged for ownership risk and tied to FR 016/017.
- `src/theme/palettes.ts` because Palettes are ported from the design source for visual parity; edits change the flame look that the spec and design expect.
- `src/components/Calendar/CalendarSheet.tsx` because Hosts the swipe-up calendar that is the only UI path for logging, editing, and clearing scores, so regressions block core use.
- `src/screens/BonfireScreen.tsx` because Top-level screen wiring stores, hooks, and the Skia scene together; flagged by analysis for import-cycle and ownership risk.
- `jest.setup.js` because Global test environment setup (including AsyncStorage mocking the contract tests rely on); changes can make all tests pass or fail spuriously.

## Never-Touch Paths

- `gardener/**` because This is the maintenance tool's own directory, and the tool should not edit itself.
- `specs/**/contracts/**` because Contracts are frozen interface definitions that the spec treats as authoritative.
- `specs/**/design/**` because Design references are source material for the visual direction and must not be altered by automation.
- `specs/**/spec.md` because Product specs are the authoritative statement of scope and fix/no-fix policy.
- `BonfireDesign/**` because BonfireDesign/ is the read-only source of truth for the design and must not be modified. (from specs/001-bonfire-productivity-tracker/plan.md#Constitution Check)
- `specs/002-achievement-flame-unlocks/checklists/requirements.md` because Achievement conditions must never require low scores, low averages, lowered scores, or intentionally breaking or extinguishing a streak or fire (FR-011a, FR-011b). (from specs/002-achievement-flame-unlocks/checklists/requirements.md#Specification Quality Checklist: Achievement-Locked Flame...)
- `src/domain/streak*` because Fire Health must not change streak survival rules; streak logic is out of bounds for this feature. (from specs/007-fire-health/spec.md#Feature Specification: Fire Health)
- `**/.env*` because secrets must never be modified by Gardener.
- `**/secrets/**` because secret material requires human handling.
- `GARDENER.md` because Gardener's own rules change only through a reviewed constitution PR.
- `.agents/skills/**` because Agent skill files define project workflow instructions and are not application code.
- `.claude/skills/**` because Agent skill files define project workflow instructions and must stay in sync with the spec kit tooling.
- `src/data/**/v1 storage key literal` because The versioned AsyncStorage key is the migration anchor for saved scores; renaming it without a migration loses user data.

## Autonomous Fixes Allowed

- `lint_format`: kept from the current constitution
- Under the current no_autonomy classification, make no autonomous code changes; only report findings.
- If autonomy is later permitted, limit to prettier formatting and eslint --fix on non-protected files under src/components/Settings or __tests__ with no behavior change.

## Assisted Fixes Allowed

- `dependency_patch`: kept from the current constitution
- `tests`: Adding or fixing Jest tests under __tests__ is low risk, provided tests assert the spec rules rather than changing rule behavior
- `complexity_reduction`: Splitting overly complex functions in fire, achievement, or flame-model code risks altering deterministic recomputation, so a human should review the diff against the spec
- `requirement_mismatch`: Where a fix changes spec assumptions (e.g., gesture supersedes prior edge swipe), the discrepancy should be reviewed rather than silently adapted (source: specs/003-ui-flame-polish/checklists/requirements.md#Specification Quality Checklist: UI & Flame Polish Fixes)
- Type-level fixes under strict TypeScript that preserve runtime behavior in src/components and src/hooks, reviewed by a maintainer.
- Adding missing unit tests for contract guarantees (for example, fire.ts behavior table rows or settingsStore invalid-color fallback) without changing production logic.
- Dependency patch updates for jest-expo, eslint-config-expo, or @types packages, verified by the full test run.

## Advisory-Only Areas

- `refactoring`: Restructuring the fire engine or flame rendering should only be suggested, not applied, because fidelity to the design must be preserved (source: specs/001-bonfire-productivity-tracker/research.md#Phase 0 Research: Bonfire Productivity Tracker (design-fa...)
- `api_behavior`: The settings store public API (setFlameStyle accepting locked ids and ignoring unknown ids) is a contract, so changes should be proposed for review rather than made automatically
- Fire scoring rules (gap tolerance, strength contribution curve, extinguish policy) because they are product decisions defined in the spec.
- Skia and Reanimated rendering performance on device, which needs manual inspection.
- Achievement thresholds and unlock timing for collectible flame styles.
- Fire Health labels (Faint, Steady, Bright, Radiant) and atmosphere tuning from local time.

## Architecture Boundaries

- The fire engine is pure and framework-free: it performs no I/O, uses no React, and never calls Date.now(); today is passed in so results are deterministic. (sources: specs/001-bonfire-productivity-tracker/contracts/fire-engine.md#Contract: Fire Engine (`src/domain/fire.ts`))
- All persistence is isolated in the data layer, and the rest of the app must never touch AsyncStorage directly. (sources: specs/001-bonfire-productivity-tracker/contracts/entries-store.md#Contract: Entries Store (`src/data/entriesStore.ts`) & `u...)

- Scores must be integers 1–5 and cannot be set for future dates; invalid writes are rejected as no-ops. (sources: specs/001-bonfire-productivity-tracker/contracts/entries-store.md#Contract: Entries Store (`src/data/entriesStore.ts`) & `u...)
- Two consecutive missed past days extinguish the fire, and today being unscored is not counted as a miss. (sources: specs/001-bonfire-productivity-tracker/contracts/fire-engine.md#Contract: Fire Engine (`src/domain/fire.ts`))
- The flame visual mapping is pure and derived from strength via the soft-cap intensity function, with height non-decreasing in strength for lit fires. (sources: specs/001-bonfire-productivity-tracker/contracts/flame-and-theme.md#Contract: Flame Model & Theme (`src/components/Bonfire/fl...)
