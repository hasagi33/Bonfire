- `src/theme/palettes.ts` because Pure color helpers and glow derivation feed all surrounding-light rendering and must keep behavior and the default look, so changes need human review. - `src/components/Settings/FlameRow.tsx` because Locked-row rejection and disabled accessibility state gate equipping and are critical to the flame selection guard, so changes need human review. (from specs/003-ui-flame-polish/contracts/locked-selection.md#Contract: Locked-Flame Selection Guard)
- `src/screens/BonfireScreen.tsx` because The equip wrapper guards persistence of flame selection by unlock state and owns the shared progress value, so changes need human review. (from specs/003-ui-flame-polish/contracts/locked-selection.md#Contract: Locked-Flame Selection Guard)

- `src/components/Bonfire/Embers.tsx` because Particle gradient fades must derive from each particle's color, so changes need human review. (from specs/003-ui-flame-polish/contracts/glow-derivation.md#Contract: Palette-Derived Glow (palettes.ts + fire scene))
- `BonfireDesign/flame-profiles.js` because Authoritative 20-profile design data that the product profiles must match. (from specs/004-flame-visual-profiles/plan.md#Implementation Plan: Flame Visual Profiles)
- `src/domain/fire.ts` because Pure fire engine that is the test oracle for fire state; contract forbids I/O, React, or Date.now(), so changes can silently alter every derived fire state.
- `src/data/entriesStore.ts` because Sole persistence boundary for scores and notes; the contract requires loadEntries never to throw and a round trip to deep-equal saved data.

- `src/components/Bonfire/flameModel.ts` because Pure flame math with contract guarantees (intensity(0)===0, strict monotonicity, soft cap) checked by flameModel.test.ts.
- `src/domain/achievements.ts` because Derives unlockable flame styles from streak and time thresholds; changes can revoke or grant user progress.
- `src/domain/flames.ts` because Flame style catalog that achievements and settings depend on; renaming or removing ids breaks saved selections.
- `src/hooks/useSettings.ts` because Validates the flame color enum and persists it; flagged for ownership risk and tied to FR 016/017.
- `src/theme/palettes.ts` because Palettes are ported from the design source for visual parity; edits change the flame look that the spec and design expect.
- `src/components/Calendar/CalendarSheet.tsx` because Hosts the swipe-up calendar that is the only UI path for logging, editing, and clearing scores, so regressions block core use.
- `src/screens/BonfireScreen.tsx` because Top-level screen wiring stores, hooks, and the Skia scene together; flagged by analysis for import-cycle and ownership risk.
- `jest.setup.js` because Global test environment setup (including AsyncStorage mocking the contract tests rely on); changes can make all tests pass or fail spuriously.

## Never-Touch Paths

- `specs/**` because Product specs and contracts are the authoritative scope and fix/no-fix policy; automation must not rewrite them.
- `gardener/**` because Maintenance tool's own configuration and output; self-modification is outside this repository's scope.
- `src/domain/fireStrength*` because Fire strength math must not be changed by Fire Health; the spec says fire strength values must stay identical (SC-003), so the fire strength code is off limits for health changes. (from specs/007-fire-health/spec.md#Feature Specification: Fire Health)
- `**/.env*` because secrets must never be modified by Gardener.
- `**/secrets/**` because secret material requires human handling.
- `GARDENER.md` because Gardener's own rules change only through a reviewed constitution PR.
- `specs/**` because Product specs and contracts are the authoritative statement of scope and fix policy and are maintained by humans.
- `.agents/skills/**` because Agent skill files define project workflow instructions and are not application code.
- `.claude/skills/**` because Agent skill files define project workflow instructions and must stay in sync with the spec kit tooling.
- `src/data/**/v1 storage key literal` because The versioned AsyncStorage key is the migration anchor for saved scores; renaming it without a migration loses user data.

## Autonomous Fixes Allowed

- `lint_format`: kept from the current constitution
- Under the current no_autonomy classification, make no autonomous code changes; only report findings.
- If autonomy is later permitted, limit to prettier formatting and eslint --fix on non-protected files under src/components/Settings or __tests__ with no behavior change.

## Assisted Fixes Allowed

- `dependency_patch`: kept from the current constitution
- `tests`: Adding unit tests for pure domain modules such as fire, achievements, and flames is low-risk and verifiable with the existing Jest setup
- `complexity_reduction`: Rendering components like Flame.tsx, Embers.tsx, and FireScene.tsx are animation-heavy Skia and Reanimated code, so simplifications need human review for visual fidelity
- Type-level fixes under strict TypeScript that preserve runtime behavior in src/components and src/hooks, reviewed by a maintainer.
- Adding missing unit tests for contract guarantees (for example, fire.ts behavior table rows or settingsStore invalid-color fallback) without changing production logic.
- Dependency patch updates for jest-expo, eslint-config-expo, or @types packages, verified by the full test run.

## Advisory-Only Areas

- `requirement_mismatch`: kept from the current constitution
- `api_behavior`: AsyncStorage keys and the settings schema are persisted user data; changes should be advised, not automated, and must follow the v1 to v2 migration
- `migrations`: The flameColor to flameStyle settings migration and stored score history are user data; any data-shape change needs a human-reviewed migration plan
- Fire scoring rules (gap tolerance, strength contribution curve, extinguish policy) because they are product decisions defined in the spec.
- Skia and Reanimated rendering performance on device, which needs manual inspection.
- Achievement thresholds and unlock timing for collectible flame styles.
- Fire Health labels (Faint, Steady, Bright, Radiant) and atmosphere tuning from local time.

## Architecture Boundaries

- Fire math must stay pure and framework-free: no I/O, no React, and no Date.now() inside the fire engine, with today passed in. (sources: specs/001-bonfire-productivity-tracker/contracts/fire-engine.md#Contract: Fire Engine (`src/domain/fire.ts`))
- All persistence must be isolated in the data layer, and the rest of the app must never access AsyncStorage directly. (sources: specs/001-bonfire-productivity-tracker/contracts/entries-store.md#Contract: Entries Store (`src/data/entriesStore.ts`) & `u...)
- The fire engine output (FireState) must never be persisted; it is derived from entries and today on every change. (sources: specs/001-bonfire-productivity-tracker/data-model.md#Phase 1 Data Model: Bonfire Productivity Tracker)
- The calendar colors cells from raw scores, and FireState deliberately has no per-day contribution map. (sources: specs/001-bonfire-productivity-tracker/data-model.md#Phase 1 Data Model: Bonfire Productivity Tracker)
- Storage keys are versioned (bonfire.entries.v1, bonfire.settings.v1; settings later bonfire.settings.v2) so future schema changes can migrate. (sources: specs/001-bonfire-productivity-tracker/contracts/entries-store.md#Contract: Entries Store (`src/data/entriesStore.ts`) & `u...; specs/002-achievement-flame-unlocks/contracts/settings-store.md#Contract: Settings Store v2 (`src/data/settingsStore.ts`...)
- The fire engine is a pure, framework-free domain module (src/domain/fire.ts) that must mirror BonfireDesign/logic.js exactly so app behavior matches the design oracle, and BonfireDesign/ is the design source of truth to which visuals must be matched. (sources: specs/001-bonfire-productivity-tracker/research.md#Phase 0 Research: Bonfire Productivity Tracker (design-fa...; specs/001-bonfire-productivity-tracker/tasks.md#Tests for User Story 1 ⚠️ (write first, ensure they FAIL))
- The flame intensity curve (1 - e^(-strength/14)) and related height/glow/brightness formulas are ported verbatim into flameModel.ts so the flame scales like the design. (sources: specs/001-bonfire-productivity-tracker/research.md#Phase 0 Research: Bonfire Productivity Tracker (design-fa...)
